# Fractal Factory: правила

Правила для людей и агентов, которые вместе делают программную систему. Они отвечают на один вопрос: кто, где и как принимает решения, чтобы человек мог отвечать за систему, которую пишут агенты.

Это слой принятия решений, а не полная методология. Как писать и проверять код одной маленькой задачи, определяют текущие практики, их можно менять.

Как пользоваться: скопируй этот файл в проект и сошлись на него из `AGENTS.md` или `CLAUDE.md`. Файл [SOURCES.md](SOURCES.md) нужен читателю, а не агенту: он связывает слова методологии с известными понятиями.

## Слова

Примеры ниже взяты из одной системы: интернет-магазин с узлами «Клиенты», «Заказы» и «Доставка».

| Слово | Значение | Пример |
|---|---|---|
| Узел | Часть системы. У него есть «снаружи» (что он обещает) и «внутри» (как устроен). | «Клиенты» |
| Обещание | То, что узел гарантирует тем, кто им пользуется. | «Вернуть адрес для печати» |
| Сценарий | Запись одного обещания из четырёх частей: условия, воздействие, отклик, мера. Его можно запустить. | См. раздел «Записи» |
| Родитель, ребёнок | Родитель отвечает за свой результат и выбор детей. Каждый ребёнок управляет собственным контрактом. | «Клиенты» — родитель «Хранилища» |
| Корень | Узел без родителя: вся система или независимый модуль. | «Магазин» |
| Потребитель, поставщик | Потребитель пользуется поставщиком. | «Доставка» — потребитель «Клиентов» |
| Проход | Прямые обращения узла к операциям детей и независимых поставщиков в одном сценарии, в порядке вызова и с числом обращений. | `Заказы.список` — 1 раз, `Клиенты.найтиМного` — 1 раз |
| Словарь | Слова предметной области узла и их значения. Одно понятие — одно слово, одно слово — одно значение. | «Адрес для печати» — адрес клиента одной строкой, готовой для накладной |
| Решение | Выбор между вариантами, записанный вместе с причиной. | «Адрес для печати отдаётся одной строкой» |
| Значимое решение | Решение, которое заметно снаружи узла или на котором будут строить другие узлы. | Формат адреса в ответе «Клиентов» |
| Продуктовое решение | Значимое решение, разницу в котором заметит пользователь продукта. | Какие поля в форме заявки |
| Техническое решение | Значимое решение, разницу в котором заметят только соседние узлы. | Хранить заявки в базе или в файле |
| Следствие | Выбор, который вытекает из решения, явно утверждённого человеком. | Второй модуль хранит данные в той же базе, что и первый |
| Ответственный | Человек, которому выносятся решения узла. | Анна отвечает за «Клиентов» |
| Ручка | Настройка: кто принимает значимые решения. | «Согласование» |
| Сводка | Решения, которые агент принял без человека, с причинами. | |
| Проработка | Режим работы: вопрос известен, ответа нет. Результат — решения и обещания. | Выбираем, на какие части делить «Заказы» |
| Поставка | Режим работы по принятым обещаниям. Результат — код и результаты проверок. | Пишем «Клиентов» по их сценариям |
| Скелет | Самая тонкая работающая сборка узла: связи между детьми настоящие, тела детей примитивные. | |

## Правила

Номер правила постоянный и сквозной: новое правило получает следующий номер по файлу и ставится в свой раздел, поэтому внутри раздела номера идут не подряд. Ссылки на правила по номеру не меняются.

### Узел

- **1. Владение образует дерево внутри каждого корня.** У ребёнка один родитель. Корень может пользоваться другими корнями, а любой узел — обещаниями своих прямых поставщиков.
- **2. Узел должен быть понятен.** Человек, который видит узел впервые, разбирается в нём за отведённое время, открыв только запись узла, его собственный код и обещания детей и других прямых поставщиков. Проверяет это не автор изменения. Чем именно проверять, определяет выбранная практика (правило 30).
  - Исключение касается только внутреннего устройства неделимого алгоритма (правило 4). Его можно разбирать дольше. За отведённое время по-прежнему должно быть понятно, что узел обещает, где проходит граница алгоритма, почему он здесь нужен и как устроен остальной код узла.
- **3. Новый узел заводится только по двум причинам.**
  - Существующий узел нельзя проверить снаружи, в нём не разобраться за отведённое время или неудачную попытку дорого выбросить.
  - Решение трудное или может измениться, и его надо отгородить, чтобы оно не задерживало остальное.
- **4. Границу проводят по решению, которое узел прячет.** У каждого узла названо, что он прячет. Проверка: спрятанное решение меняется, а обещания узла нет.
  - Хорошая граница уменьшает объём знаний, нужных потребителю. Когда проводишь или меняешь границу, возьми сценарий потребителя и назови, что ему достаточно знать для вызова и в каких деталях ему больше не придётся разбираться. Если ему по-прежнему нужны те же детали, пересмотри границу или обещание.
  - Например, «Доставка» передаёт номер клиента и получает строку для накладной. Порядок полей и правила пропуска пустых полей знают только «Клиенты». Если строку по этим правилам всё ещё собирает «Доставка», граница их не спрятала.
  - Первый разрез системы идёт по языку предметной области: граница там, где одно слово начинает значить разное.
  - Слово, по которому проведена граница, записано в словаре узла, где оно значит своё. Внутри узла одно понятие называется одним словом, а одно слово значит одно.
  - Что меняется вместе или опирается на одно знание, лежит в одном узле.
  - Узел, который повторяет обещания соседа, сливается с ним.
  - Неделимый алгоритм оставляют целиком. Известный называют по имени и дают ссылку на описание, самодельный помечают как сложный.
- **5. Собственная часть остаётся ребёнком, пока ею напрямую пользуется только её родитель.** Несколько сценариев одного узла считаются одним потребителем. При появлении второго узла-потребителя часть выделяют в независимый модуль со своим ответственным. Это значимое решение.
- **6. Потребитель объявляет использование.** Узел обращается к поставщику только через его публичные обещания, записывает, чем пользуется, и приносит проверки своих ожиданий. Готовый независимый модуль или внешний сервис остаётся поставщиком даже при одном потребителе в проекте.
- **7. У данных один владелец.** Узел не читает и не пишет чужие данные в обход обещаний владельца.
- **8. Сквозные правила записаны у предка.** Формат идентификаторов, обработка ошибок, правила работы с данными и слова словаря наследуются всеми узлами ниже. Ребёнок может дать слову другое значение, только записав его в своём словаре: это значит, что здесь проходит граница.

### Обещание

- **9. Обещание записано сценарием.** В сценарии четыре части: условия, воздействие, отклик, мера. Условия называют данные и нагрузку. Сценарий запускается снаружи узла.
- **10. Позднее свидетельство помечено.** Если условия нельзя воспроизвести до эксплуатации, сценарий помечен «проверяется поздно». Человек видит список таких обещаний.
- **11. Обещания родителя остаются у родителя.** Дети делают простые операции и не знают, зачем они родителю. Родитель проверяет свои обещания на настоящей сборке.
- **12. Если сценарий обращается к другому узлу, у него есть проход.** Правило действует и у узла без детей. Вызовы внутри поставщика описывает сам поставщик. Обещание ребёнка, которого нет ни в одном проходе родителя и для которого ни один потребитель не принёс проверку (правило 6), — кандидат на удаление вместе со своими проверками. Обещаний корня и обещаний, которыми пользуется другой корень, это не касается: их потребители снаружи. Удаление обещания и его проверки — значимое решение у узла, чьё это обещание (правила 17, 20).
- **13. Узел с детьми начинают со скелета.** Сначала собирается самая тонкая работающая цепочка через всех детей. Проверки родителя идут на ней с первого дня и зеленеют по мере роста детей. Скелет не разбирают.

- **32. Сбой на шве оставляет проверку.** Если сборка родителя красная при зелёных детях или сбой найден в эксплуатации, сначала пишется проверка, которая его воспроизводит, потом починка. Если неверен проход или логика родителя, проверка остаётся у родителя. Если не хватает обещания ребёнка, родитель показывает сбой своим сценарием: ребёнок принимает новое обещание и записывает его своим сценарием без ссылки на родителя, либо отказывает, и тогда родитель меняет разбиение и записывает это у себя. Новое или изменённое обещание — значимое решение у узла, чьё оно (правила 17, 20), работа возвращается в проработку (правило 14). Кому обещание нужно, видно из проходов (правило 21).

### Решение

- **14. Работа всегда в одном из двух режимов.** В проработке ищут решения, её код в продукт не попадает. В поставке работают по принятым обещаниям и не меняют их молча: если обещание оказалось неверным, работа возвращается в проработку.
- **15. Эксперимент требует вопроса и бюджета.** Сначала названо, на какой вопрос он отвечает и сколько на него тратится.
- **16. Кто решает.**
    - Необратимое действие человек подтверждает заранее, при любой настройке. Написать код можно, подтверждение нужно перед исполнением.
    - Следствие агент делает сам и называет запись, из которой оно следует. Следствие не может вводить новый узел, хранилище, внешний эффект или зависимость.
    - Значимое решение идёт по ручке.
    - Всё остальное решает агент.
- **17. Значимое или нет, определяет не тот, кто решил.** Признаки, видимые в изменении: правка или удаление существующей проверки, новое или изменённое обещание, новое использование чужого узла, новый узел, хранилище, внешний эффект, зависимость.
- **18. Сомнение поднимает маршрут.** Если агент сомневается, значимое ли решение, оно значимое. Уверенность агента маршрут не понижает.
- **19. Человеку выносят свойство, а не механизм.** «Насколько свежими должны быть данные», а не «делаем ли кеш». Агент готовит варианты с рекомендацией.
- **20. Решение записывается у одного узла.** Это узел, чьи обещания или деление на детей оно меняет. В записи есть причина, отвергнутые варианты и решение, из которого оно следует.
- **21. Что зависит от решения, вычисляется.** Это дети узла, его потребители и обещания, чьи проходы идут через затронутую операцию. Списки зависимостей руками не ведут.
- **22. Открытое решение задерживает только зависимое.** Остальная работа идёт. Фаз и общего момента передачи нет: часть берут в работу, как только для неё решено достаточно.
- **23. Человек видит решения, принятые без него.** По каждому он отмечает, согласен или нет. Прецедентом для следствий служит только решение, которое человек явно утвердил. При ручке «Полный контроль» человек проверяет каждое значимое решение. При ручке «Автономно» отметка по желанию: непросмотренное работу не держит и прецедентом не служит.
- **34. Решение показано так, чтобы человек принял его без кода.** Разница между вариантами видна сразу, форма идёт за видом разницы: таблица, схема, экран, работающий результат (он эксперимент по правилу 15). Решение помещается на один экран. Что в показанном не входит в решение, названо. Если человек не смог решить по записи, он это отмечает, и отметка считается как попытка по правилу 29. Требование действует и для решений в сводке (правило 23).
- **31. Глубину проработки задаёт цена переделки.** Значимое решение прорабатывают, пока ошибка в нём дороже эксперимента (правило 15). Цену агент оценивает сам, порога нет. В записи есть строка «Если ошибёмся»: что придётся переделать (правило 21) и можно ли откатить. При отмене решения её сверяют с тем, что пришлось переделать на деле; расхождение идёт в счёт правила 29. Оценка маршрут к человеку не понижает (правило 18); «откатить нельзя» — необратимое по правилу 16.

### Ручка

У ручки три положения. Она ставится отдельно для продуктовых и технических решений и переопределяется для любого узла вместе с его детьми.

| Положение | Значимые решения | Зависимая работа |
|---|---|---|
| Автономно | Решает агент, человек видит потом | Не ждёт |
| Согласование (по умолчанию) | Решает человек | Ждёт человека |
| Полный контроль | Решает человек и утверждает каждую поставку | Ждёт человека |

Намерение корневого узла человек задаёт сам при любом положении.

### Люди

- **24. У узла один ответственный.** Если он не назван, отвечает ответственный за родителя. Решение идёт ответственному за узел, у которого оно записано.
- **25. На связи между узлами разных людей записано, кто подстраивается.**
    - «Поставщик слушает»: сломать проверку потребителя можно только с согласия его ответственного. Умолчание внутри одного корня.
    - «Потребитель подстраивается»: поставщик меняет сам, потребитель чинит у себя. Умолчание для чужого корня и для поставщика со многими потребителями.
    - Если стороны хотят разного, они разговаривают. В худшем случае подстраивается потребитель.
- **26. Похожие узлы из разных корней показывают людям.** Ответственные разговаривают и решают сами. Процесса для этого нет.

### Код одной задачи

Эта часть заменяема. От любой практики требуется пять вещей: правила 27–30 и 33.

- **27. На входе маленькая задача с принятыми обещаниями.** Тот, кто пишет код, принятые обещания сам не меняет.
- **28. На выходе код и результат прогона.** Результат получен программой, а не словами агента.
- **29. Считаются попытки и отменённые решения.** Много попыток — сигнал делить узел, чинить обещание или звать человека.
- **30. После поставки узел остаётся понятным по правилу 2.** Проверка обязательна. Как её делать, определяют выбранные практики: статический анализ, агент с чистым контекстом, внешний сервис ревью, любое сочетание. Без выбранной проверки понятности практика не годится.
- **33. Каждую поставку сопровождают два обязательных прогона.** Это сценарии обещаний узла (правило 9) и проверка понятности (правило 30). По каждому в результате поставки стоят команда и её вывод (правило 28), красный прогон останавливает поставку. Они закрываются разными средствами; если одним, это значимое решение. Проверка, которой нет или которая не может упасть, записана как «нет», и человек видит такие строки списком, как «проверяется поздно». Всё, что программа может проверить дёшево до запуска (линтер, типы, компилятор), проверяет программа: практики это рекомендуют, а отказ записан в настройках с причиной, например «у SQL-миграций анализатора нет». В настройках каждая проверка названа практикой и командой. Ослабить проверку в узле — значимое решение (правило 17).

Практика по умолчанию: сначала проверка, потом код; принятую проверку не правят; после зелёной проверки код приводят в порядок, не меняя обещаний.

## Записи

Каждый узел — папка. В ней лежит файл `NODE.md` и код узла. Ребёнок — вложенная папка. Независимый модуль — папка верхнего уровня.

### Запись узла

```markdown
# Клиенты

- Ответственный: Анна
- Прячет: как хранится и проверяется адрес клиента

## Словарь

- Адрес для печати — адрес клиента одной строкой, готовой для накладной
- Клиент — человек, у которого есть хотя бы один заказ

## Обещания

### Вернуть адрес для печати

- Условия: в хранилище 100 000 клиентов
- Воздействие: «Доставка» запрашивает адрес клиента по номеру
- Отклик: адрес одной строкой, готовой для накладной
- Мера: 95% ответов быстрее 50 мс
- Проверка: `tests/address_for_print_test`
- Проход: `Хранилище.найти` — 1 раз

## Дети

- Хранилище — прячет, в какой базе лежат клиенты

## Использует

- Хранилище — собственный ребёнок

## Решения

### 1. Адрес для печати отдаётся одной строкой

- Определяет: обещание «Вернуть адрес для печати»
- Вид: техническое
- Статус: принято
- Почему: «Доставка» не зависит от того, как адрес хранится
- Если ошибёмся: переделать «Доставку» и накладные, откатить можно
- Отвергнуто: отдавать поля адреса — тогда «Доставка» ждёт решения о формате хранения
- Следует из: нет
- Решил: Анна, 2026-11-25
```

Правила заполнения:

- **Словарь.** Агент собирает его из разговора с человеком, а не придумывает. Слово, которого нет в словаре, в обещаниях, коде, базе и интерфейсе узла не используется: сначала оно записывается. Изменение значения слова, на котором стоит обещание, — решение об этом обещании.
- **Обещания.** Если сценарий вызывает операцию другого узла, укажите её в проходе по правилу 12. Сценарий без проверки помечают «проверки нет»; человек видит такие обещания списком, как «проверяется поздно».
- **Использует.** Укажите прямого поставщика. Если за узлы отвечают разные люди, укажите, кто подстраивается по правилу 25. Пример записи — «Клиенты — поставщик слушает».
- **Статус решения.** «Открыто», «принято» или «отменено». У открытого записаны варианты и рекомендация.
- **Решил.** Имя человека или «агент». Если решил агент, ниже строка «Отметка человека: не смотрел, согласен или не согласен». Сводка — это все решения агента с отметкой «не смотрел».
- **Следствие** отдельной записью не оформляют: агент называет исходное решение в сообщении коммита.

### Настройки

Лежат в `NODE.md` корня. Любой узел может переопределить их для себя и своих детей.

```markdown
## Настройки

- Продуктовые решения: согласование
- Технические решения: согласование
- Время на разбирательство в узле: 30 минут
- Практики: П1, П3, П5, П14, П52, П54
- Проверки: сценарии — П1, П3, `make test`; статический разбор — П5, `make lint`; понятность — П52
- Пределы статического разбора: функция не длиннее 60 строк
```

## С чего начать новую систему

1. Человек называет намерение корня и ставит ручку.
2. Агент спрашивает, какие практики кода одной задачи применять, и записывает выбор в настройки корня. Список практик лежит в `AGENTS.md`. Среди выбранных обязательно есть две проверки (правило 33), статический разбор рекомендован и способ показывать решения человеку (правило 34).
3. Проработка корня снаружи: его обещания записаны сценариями. Слова, которыми человек описывает систему, агент записывает в словарь корня и уточняет, где значение неясно.
4. При проработке корня изнутри назовите детей и решения, которые они прячут. Уже существующих поставщиков укажите в «Использует». Для сценариев запишите прямые обращения по правилу 12.
5. Скелет корня: настоящие связи между детьми, примитивные тела.
6. Каждый ребёнок проходит те же шаги. Дети, которые не ждут открытых решений, идут одновременно.
